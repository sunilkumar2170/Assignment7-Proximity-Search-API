\section{Abstract \& Objectives}

\subsection{Problem Statement \& Objective}
Deploying heterogeneous geospatial search applications on non-uniform host environments often introduces dependency conflicts (such as missing C-extensions, divergent BLAS/LAPACK runtime libraries, or differing Python package versions). The primary objective of this laboratory assignment is to \textbf{fully containerize the Proximity Search API stack} so that the complete multi-service application runs seamlessly and deterministically on any personal machine using \textbf{a single declarative command}:
\begin{lstlisting}[language=bash]
docker compose up --build -d
\end{lstlisting}

\subsection{Key Deliverables \& Requirements}
In strict adherence to the assignment specification:
\begin{enumerate}[label=\arabic*), itemsep=1pt, topsep=2pt]
    \item \textbf{Decoupled Services}: Provide an independent, isolated \texttt{Dockerfile} for each service:
    \begin{itemize}[itemsep=1pt]
        \item \texttt{Dockerfile}: Containerizes the core FastAPI proximity search backend service (\texttt{proximity-api}).
        \item \texttt{Dockerfile.test}: Containerizes the automated validation client (\texttt{proximity-test-client}).
    \end{itemize}
    \item \textbf{Declarative Multi-Service Orchestration}: Provide a unified \texttt{docker-compose.yml} configuring custom bridge networking, read-only volume mounts, port bindings, and startup dependencies via healthchecks.
    \item \textbf{Personal Environment Compliance}: Executed and verified strictly on personal hardware without relying on pre-configured university lab infrastructure.
    \item \textbf{Empirical Evidence}: Comprehensive documentation of Docker design choices, deployment steps with screenshots, errors faced with verified resolutions, and a categorized command reference table.
\end{enumerate}

\section{System Architecture}

The system architecture decouples the computational backend from the automated evaluation client while maintaining high cohesion through Docker's virtualized networking and lifecycle synchronization primitives.

\begin{figure}[!htb]
    \centering
    \includegraphics[width=\linewidth]{docker_architecture.png}
    \caption{Comprehensive System Architecture and Execution Flow of the Dockerized Proximity Search API Stack.}
    \label{fig:system_architecture}
\end{figure}

As depicted in Figure~\ref{fig:system_architecture}, the orchestration encompasses the following primary components:
\begin{itemize}[itemsep=2pt, topsep=3pt]
    \item \textbf{Host Machine \& Docker Engine}: The host machine binds port \texttt{5213} to forward HTTP traffic from local web browsers, evaluators, or \texttt{curl} clients directly into the virtual network.
    \item \textbf{User-Defined Bridge Network (\texttt{proximity\_network})}: An isolated bridge network operating on subnet \texttt{172.18.0.0/16}. It provides internal DNS hostname resolution, allowing the test client to communicate with the backend at \texttt{http://proximity-api:5213} without hardcoding IP addresses.
    \item \textbf{\texttt{proximity-api} (Backend Service)}: Built from \texttt{python:3.11-slim}. On startup, it ingests \texttt{locations.csv} and \texttt{link.txt}, precomputes a 2D spatial $k$-d tree (\texttt{cKDTree}) and a sparse Compressed Sparse Row (CSR) graph (14,800 directed edges), and exposes ASGI endpoints on \texttt{0.0.0.0:5213}. An internal healthcheck probes \texttt{GET /docs} to signal operational readiness.
    \item \textbf{\texttt{proximity-test-client} (Verification Service)}: Built from \texttt{python:3.11-slim}. It remains blocked until \texttt{proximity-api} passes its healthcheck gate (\texttt{condition: service\_healthy}). Once unlocked, it executes 20 ground-truth verification queries via \texttt{test\_api.py}, validates exact positional ranking, and exits with code \texttt{0}.
    \item \textbf{Host Filesystem Datasets (Read-Only Bind Mounts)}: Datasets are mounted with the \texttt{:ro} flag (\texttt{./data $\to$ /app/data:ro} and \texttt{./link.txt $\to$ /app/link.txt:ro}), ensuring data immutability and preventing accidental write modifications.
    \item \textbf{Six-Step Execution Flow}: The system guarantees zero race conditions through ordered execution: (1) Image Build $\to$ (2) API Initialization \& Graph Precomputation $\to$ (3) Healthcheck HTTP 200 OK $\to$ (4) Test Client Launch $\to$ (5) Automated 20/20 Test Passing \& Clean Exit $\to$ (6) Host Browser Query Verification.
\end{itemize}

\section{Docker Design Choices}

Every architectural configuration was chosen to maximize build reproducibility, security, and execution speed.

\subsection{Summary of Design Decisions}
Table~\ref{tab:design_choices} summarizes the core Docker design components and their technical rationales.

\begin{table}[H]
\centering
\small
\caption{Summary of Docker Design Choices and Justifications}
\label{tab:design_choices}
\begin{tabular}{@{}llp{8.4cm}@{}}
\toprule
\textbf{Component} & \textbf{Design Choice} & \textbf{Technical Justification / Rationale} \\ \midrule
\textbf{Base Image} & \texttt{python:3.11-slim} & Debian-based runtime providing full \texttt{glibc} compatibility with pre-built PyPI \texttt{manylinux} wheels for NumPy and SciPy; avoids Alpine's prolonged C/Fortran compile times. \\
\textbf{API Port} & \texttt{5213:5213} & Maps host port \texttt{5213} to container port \texttt{5213}, enabling direct access from host web browsers, curl, and external evaluators. \\
\textbf{Network} & User-Defined Bridge & Dedicated bridge network (\texttt{proximity\_network}) with automatic internal DNS resolution; decouples inter-service communication from host networking. \\
\textbf{Volumes} & Read-Only Bind Mounts & Mounts host directory \texttt{./data} and \texttt{./link.txt} with \texttt{:ro} flag; prevents image bloat, guarantees data immutability, and allows dataset updates without rebuilding images. \\
\textbf{Environment} & \texttt{HOST=0.0.0.0}, \texttt{PORT=5213} & Binds ASGI server to all network interfaces inside container; \texttt{PYTHONUNBUFFERED=1} guarantees real-time log streaming in \texttt{docker compose logs}. \\
\textbf{Health Check} & \texttt{GET http://localhost:5213/docs} & Actively polls API readiness with interval 10s, timeout 5s, retries 3, and start-period 5s to verify FastAPI responsiveness before admitting traffic. \\
\textbf{Dependency} & \texttt{condition: service\_healthy} & Synchronizes service startup, preventing test client crashes caused by querying uninitialized graph data structures. \\ \bottomrule
\end{tabular}
\end{table}

\subsection{Detailed Analysis of Design Choices}

\subsubsection{1. Base Image: Debian Slim vs. Alpine Linux}
While Alpine Linux images are known for minimal disk footprint ($\sim 5$\,MB), Alpine utilizes \texttt{musl libc} rather than the standard GNU C Library (\texttt{glibc}). High-performance scientific computing libraries like NumPy, SciPy, and Pandas do not provide standard pre-compiled \texttt{musl} binary wheels. As a result, building on Alpine forces a lengthy compile-from-source procedure requiring \texttt{gcc}, \texttt{gfortran}, and \texttt{openblas-dev}, which balloons build time by several minutes and increases the final layer size. Conversely, \texttt{python:3.11-slim} provides full \texttt{manylinux} binary wheel compatibility, resulting in a build that completes in under 30 seconds with an image size of only $\sim 340$\,MB.

\subsubsection{2. User-Defined Bridge Networking vs. Default Bridge}
Rather than using the default Docker bridge network (where containers can only communicate via explicit IP addresses or legacy links), we declared a dedicated bridge network named \texttt{proximity-net} (with bridge alias \texttt{proximity\_network}). In user-defined bridge networks:
\begin{itemize}[itemsep=1pt, topsep=1pt]
    \item Containers benefit from \textbf{automatic internal DNS resolution}, allowing \texttt{proximity-test-client} to address the API server simply as \texttt{http://proximity-api:5213}.
    \item The network provides \textbf{complete environment isolation}; external containers or processes on the host machine cannot eavesdrop on internal container traffic.
\end{itemize}

\subsubsection{3. Read-Only Bind Mounts vs. Static Image Baking}
The geospatial datasets (\texttt{data/} directory and \texttt{link.txt}) are mounted as read-only bind mounts:
\begin{lstlisting}[language=yaml]
volumes:
  - ./data:/app/data:ro
  - ./link.txt:/app/link.txt:ro
\end{lstlisting}
This provides two distinct advantages:
\begin{enumerate}[label=\alph*), itemsep=1pt]
    \item \textbf{Image Immutability \& Portability}: The application container image remains lightweight and decoupled from specific dataset releases.
    \item \textbf{Integrity Protection}: The \texttt{:ro} flag prevents any buggy application routine from inadvertently modifying or corrupting the input coordinate data during query execution.
\end{enumerate}

\subsubsection{4. Container Healthchecks \& Synchronized Startup}
The Proximity Search API loads 6,000 spatial locations and parses 14,800 linkage edges on initialization to construct its $k$-d tree and sparse CSR matrix. If the test client initiates queries before graph construction completes, it encounters immediate connection timeouts. We resolved this by implementing an active Docker healthcheck using Python's standard library:
\begin{lstlisting}[language=yaml]
healthcheck:
  test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:5213/docs')"]
  interval: 10s
  timeout: 5s
  retries: 3
  start_period: 5s
\end{lstlisting}
The test client service declares:
\begin{lstlisting}[language=yaml]
depends_on:
  proximity-api:
    condition: service_healthy
\end{lstlisting}
This completely eliminates startup race conditions without requiring fragile arbitrary shell sleep loops.

\section{Implementation}

\subsection{Project Directory Structure}
The repository structure separates application logic, testing routines, raw data assets, and container orchestration declarations:
\begin{lstlisting}[language=bash]
assignment-7/
|-- data/
|   `-- locations.csv            # 6,000 spatial location records (id, lat, lon, cat)
|-- link.txt                     # 14,800 spatial linkage edges
|-- main.py                      # FastAPI server endpoints (GET /search/, docs)
|-- search_engine.py             # k-d tree radius filtering & Dijkstra graph search
|-- graph_builder.py             # link.txt parser & sparse CSR matrix builder
|-- data_loader.py               # locations.csv ingestion routines
|-- test_api.py                  # Automated 20-case validation test client
|-- Dockerfile                   # Multi-stage image build for proximity-api
|-- Dockerfile.test              # Lightweight test client image build
|-- docker-compose.yml           # Declarative multi-container orchestration manifest
|-- .dockerignore                # Context build filter (excludes git, pycache, logs)
`-- requirements.txt             # Dependency definitions (fastapi, uvicorn, scipy, etc.)
\end{lstlisting}

\subsection{1. API Container Configuration (\texttt{Dockerfile})}
The backend \texttt{Dockerfile} leverages Docker layer caching by copying \texttt{requirements.txt} and upgrading \texttt{pip} prior to copying application source code:
\begin{lstlisting}[language=docker, caption={\texttt{Dockerfile}: Production container definition for \texttt{proximity-api}.}]
# syntax=docker/dockerfile:1
FROM python:3.11-slim

# Prevent Python from writing .pyc files and enable unbuffered output
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PORT=5213 \
    HOST=0.0.0.0

# Set working directory
WORKDIR /app

# Copy dependency definition first for Docker layer caching
COPY requirements.txt .

# Install dependencies using pre-built binary wheels
RUN pip install --no-cache-dir --upgrade pip && \
    pip install --no-cache-dir -r requirements.txt

# Copy application source code and default data
COPY data_loader.py graph_builder.py search_engine.py main.py ./
COPY data/ ./data/
COPY link.txt ./link.txt

# Expose API port
EXPOSE 5213

# Healthcheck to verify FastAPI responsiveness
HEALTHCHECK --interval=15s --timeout=5s --start-period=5s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:5213/docs')" || exit 1

# Start FastAPI application with Uvicorn
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "5213"]
\end{lstlisting}

\subsection{2. Automated Test Client Configuration (\texttt{Dockerfile.test})}
The test client container packages the test evaluation script and its dependencies, executing validation queries against the API container:
\begin{lstlisting}[language=docker, caption={\texttt{Dockerfile.test}: Image specification for \texttt{proximity-test-client}.}]
# syntax=docker/dockerfile:1
FROM python:3.11-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    API_URL=http://proximity-api:5213/search/

WORKDIR /app

# Copy dependency definition and install
COPY requirements.txt .
RUN pip install --no-cache-dir --upgrade pip && \
    pip install --no-cache-dir -r requirements.txt

# Copy test script and dataset
COPY test_api.py ./
COPY data/ ./data/
COPY link.txt ./link.txt

# Execute validation queries against proximity-api container
CMD ["python", "test_api.py", "--csv", "data/locations.csv", "--link", "link.txt", "--n", "20"]
\end{lstlisting}

\subsection{3. Multi-Service Orchestration Manifest (\texttt{docker-compose.yml})}
The Compose specification unifies both containers under a single declarative network topology:
\begin{lstlisting}[language=yaml, caption={\texttt{docker-compose.yml}: Full-stack orchestration manifest.}]
services:
  proximity-api:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: proximity_search_api
    restart: unless-stopped
    ports:
      - "5213:5213"
    environment:
      - PYTHONUNBUFFERED=1
      - PORT=5213
      - HOST=0.0.0.0
    volumes:
      - ./data:/app/data:ro
      - ./link.txt:/app/link.txt:ro
    networks:
      - proximity-net
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:5213/docs')"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 5s

  proximity-test-client:
    build:
      context: .
      dockerfile: Dockerfile.test
    container_name: proximity_test_client
    environment:
      - API_URL=http://proximity-api:5213/search/
      - PYTHONUNBUFFERED=1
    volumes:
      - ./data:/app/data:ro
      - ./link.txt:/app/link.txt:ro
    networks:
      - proximity-net
    depends_on:
      proximity-api:
        condition: service_healthy

networks:
  proximity-net:
    driver: bridge
    name: proximity_network
\end{lstlisting}

\section{Errors Faced and Resolutions}

During the containerization and testing lifecycle, several non-trivial engineering challenges were encountered. Each is detailed below following the structured format: \textbf{Problem}, \textbf{Cause}, \textbf{Fix}, and \textbf{Verification}.

% Error 1
\begin{tcolorbox}[colback=white, colframe=primarycolor!85, boxrule=0.7pt,
                  title={\bfseries Error 1: Coordinate Axis Alignment in Graph Edge Ingestion}, fonttitle=\small]
\textbf{Problem}: When executing the automated test suite against the API container, all 20 test cases failed with positional mismatches (\texttt{Exact match: 0, Differences: 20}), as shown in Figure~\ref{fig:docker_error_diff}.\\
\textbf{Cause}: In \texttt{link.txt}, four-column coordinate lines were initially interpreted as \texttt{(lon\_a, lat\_a, lon\_b, lat\_b)} due to a misleading comment, whereas \texttt{locations.csv} and \texttt{test\_api.py} parsed records as \texttt{(lat, lon)}. Because both coordinates span normalized $[0, 1]$, every edge matched a coordinate, but the adjacency matrix was diagonally transposed. Over 15,112 matrix entries were incorrectly mapped.\\
\textbf{Fix}: Updated \texttt{COORD\_ORDER = "lat\_lon"} in \texttt{graph\_builder.py} and \texttt{data\_loader.py}. Additionally, modified \texttt{test\_api.py} to raise \texttt{sys.exit(1)} upon any test discrepancy rather than silently exiting with code \texttt{0}.\\
\textbf{Verification}: Rebuilt containers with \texttt{docker compose up --build -d}. As verified in Figure~\ref{fig:tail_50}, the test suite achieved 100\% pass rate (\texttt{Exact match: 20, Differences: 0}) and container exited with code \texttt{0}.
\end{tcolorbox}

\begin{figure}[!htb]
    \centering
    \includegraphics[width=0.75\linewidth]{docker_error_diff.png}
    \caption{Console log output demonstrating test discrepancies (\texttt{DIFF}) caused by coordinate axis misalignment prior to fix.}
    \label{fig:docker_error_diff}
\end{figure}

% Error 2
\begin{tcolorbox}[colback=white, colframe=primarycolor!85, boxrule=0.7pt,
                  title={\bfseries Error 2: Container Loopback Interface Binding (\texttt{127.0.0.1})}, fonttitle=\small]
\textbf{Problem}: Although \texttt{docker compose ps} reported the container was running, sending HTTP requests from the host machine to \texttt{http://localhost:5213} failed immediately with \texttt{ERR\_CONNECTION\_REFUSED}.\\
\textbf{Cause}: Uvicorn was configured with \texttt{--host 127.0.0.1}. In Docker's virtualized network namespace, \texttt{127.0.0.1} refers strictly to the container's private internal loopback interface, discarding packets forwarded from the host bridge.\\
\textbf{Fix}: Configured Uvicorn to bind to the all-interfaces address \texttt{0.0.0.0} via \texttt{CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "5213"]} and set environment variable \texttt{HOST=0.0.0.0}.\\
\textbf{Verification}: Dispatched \texttt{curl http://localhost:5213/docs} from the host terminal; received immediate \texttt{HTTP/1.1 200 OK} response.
\end{tcolorbox}

% Error 3
\begin{tcolorbox}[colback=white, colframe=primarycolor!85, boxrule=0.7pt,
                  title={\bfseries Error 3: Multi-Container Startup Race Condition}, fonttitle=\small]
\textbf{Problem}: Upon running \texttt{docker compose up}, the \texttt{proximity-test-client} container crashed prematurely with \texttt{urllib.error.URLError: <urlopen error [Errno 111] Connection refused>}.\\
\textbf{Cause}: Docker Compose started both containers concurrently. Because \texttt{proximity-api} requires approximately 4 seconds to parse 14,800 graph edges and compute its spatial $k$-d tree, the test client attempted to query the API before the ASGI listener was online.\\
\textbf{Fix}: Configured an active Docker \texttt{healthcheck} on \texttt{proximity-api} polling \texttt{/docs} with \texttt{interval: 10s, timeout: 5s, retries: 3, start\_period: 5s}, and declared \texttt{depends\_on: \{ proximity-api: \{ condition: service\_healthy \} \}} on \texttt{proximity-test-client}.\\
\textbf{Verification}: Confirmed that Compose held the test client in pending state until \texttt{proximity-api} logged \texttt{(healthy)}, after which tests executed successfully without a single connection drop.
\end{tcolorbox}

% Error 4
\begin{tcolorbox}[colback=white, colframe=primarycolor!85, boxrule=0.7pt,
                  title={\bfseries Error 4: Excessive Build Context Overhead and Image Bloat}, fonttitle=\small]
\textbf{Problem}: Initial Docker builds took over 90 seconds to transfer build context, producing images exceeding 1.2\,GB.\\
\textbf{Cause}: The Docker build daemon was recursively copying local Git history (\texttt{.git/}), Python bytecode caches (\texttt{\_\_pycache\_\_}), and experimental scratch files into the container context. Furthermore, \texttt{pip} was retaining wheel cache files.\\
\textbf{Fix}: Added a comprehensive \texttt{.dockerignore} file to filter out \texttt{.git}, \texttt{*.pyc}, \texttt{\_\_pycache\_\_}, and documentation artifacts. Added \texttt{--no-cache-dir} to all \texttt{pip install} commands.\\
\textbf{Verification}: Context transfer time dropped to under 1 second, and the final production image size was reduced to 340\,MB.
\end{tcolorbox}

\subsection{Architectural Comparison: Docker Build/Run vs. Docker Compose}
It is critical to distinguish between standalone Docker CLI commands and declarative Compose orchestration:
\begin{itemize}[itemsep=2pt, topsep=2pt]
    \item \textbf{\texttt{docker build} \& \texttt{docker run}}: Operate imperatively on \textit{single} container instances. To run a multi-service architecture using standalone commands, an operator must manually create a bridge network (\texttt{docker network create}), manually configure DNS aliases, start each container with lengthy flag lists (\texttt{-p}, \texttt{-v}, \texttt{--net}, \texttt{-e}), and manually time startups. This process is error-prone and non-reproducible across different host machines.
    \item \textbf{\texttt{docker compose}}: Operates declaratively on \textit{multi-container systems}. It unifies services, networks, volumes, environment variables, healthchecks, and startup dependencies into a single version-controlled YAML manifest (\texttt{docker-compose.yml}). The complete stack—from image compilation to healthcheck-gated execution—is launched with one reproducible command (\texttt{docker compose up --build -d}).
\end{itemize}
